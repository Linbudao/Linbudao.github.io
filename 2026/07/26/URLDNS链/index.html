URLDNS 是反序列化一条极其经典的利用链

不执行系统命令（不能弹计算器，也不能反弹 shell）

依赖JDK自带类

并不要求目标安装 Commons Collections、BeanUtils 等第三方库

其作用是发起一次 DNS 请求，来做反序列化探测

DNSLog看到解析记录，我们就知道两件事：

  • 这个点大概率存在反序列化

  • 反序列化走到了危险对象处理逻辑

官方注释链路如下

入口点HashMap.readObject()

目标服务器接收序列化数据，准备调用ObjectInputStream.readObject()来还原对象

如果还原的是一个HashMap，会自动调用HashMap内部重写的readObject()方法

而HashMap在反序列化时，为了重建哈希表，会把序列化流里面的键值对挨个读取出来再重新计算哈希值，以此来决定它们在内存表里里面的位置

触发哈希计算 HashMap.hash(key)

重建过程中，HashMap 这种容器对象需要重新建桶，重新放entry，重新计算hash，对每一个 Key 调用 .hashCode() 方法来获取它的哈希值

关键设计： payload 中把一个 URL 对象 当作 Key 塞进了这个 HashMap 里。所以，这里实际上调用的是 URL.hashCode()

URL 类的特殊机制 URL.hashCode()

java.net.URL 类有一个特殊行为——它的 equals() 和 hashCode() 方法在比较/计算哈希值时，会顺带发起一次 DNS 查询（因为要把域名解析成 IP 来判断两个URL是否指向同一台主机）。hash() 内部会去调用 key 对象自己的 hashCode() 方法：

hashCode还有一个特点，URL会缓存已经计算过的哈希值

逻辑类似于

若hashcode值为-1时，尚未计算，它会调用 URLStreamHandler.hashCode(this) 发起DNS查询解析域名，计算出哈希值并保存到 hashCode 字段中

若hashCode!=-1时，已经计算过，直接返回缓存值

我们可以通过设置缓存值为一个不为-1的数来避免提前产生DNS查询

这里就要用到我们的反射机制了

URL的hashCode缓存字段是private，普通代码无法直接访问，就要用到反射去修改值
